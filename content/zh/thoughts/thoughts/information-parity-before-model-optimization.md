> 核心判断：Agent 失败时，先比较人类与模型在决策时真正拥有的信息。如果领域专家只凭模型看到的同一份输入就能稳定得到正确结果，优先检查模型、提示词和推理过程；如果专家必须获得模型没有的证据才能判断，优先优化系统的信息获取、筛选、路由和时机；如果相同信息本来就支持多个合理答案，先修任务契约和验收标准。

## 目标读者

- 正在设计 Agent、RAG、智能工作流或多 Agent 系统的工程师
- 经常在“换更强模型”和“增加更多编排”之间摇摆的系统设计者
- 需要复盘错误路由、错误判断、遗漏信息或不稳定输出的团队

## 为什么需要这条判断原则

Agent 做错一件事以后，团队通常会很快进入两种反应之一：

```text
模型不够强，换一个更大的模型。

系统不够完整，再加一个 Agent、一次检索或一层工作流。
```

两种做法都可能有效，但也都很容易误诊。

如果输入里已经有完整证据，只是模型没有正确使用，那么继续增加检索和 Agent，只会让
上下文更长、链路更复杂。

如果关键证据根本没有进入上下文，那么升级模型只是要求它更有把握地猜测缺失事实。

因此，我现在更倾向于先问一个反事实问题：

> 在模型实际看到的相同输入下，一个具备相关能力的人类专家能否稳定得到正确输出？

这个问题把“模型不聪明”和“系统没把题目交代完整”分开了。

## 先划分系统与推理的职责

这里的“系统侧”和“模型侧”不是严格的学术分类，而是为了找到下一步应该改哪里。

我会这样划分：

```text
系统侧负责：
- 获取必要信息
- 选择与压缩证据
- 在 Agent 之间传递信息
- 在正确的决策时点提供信息
- 保存任务状态和历史
- 提供工具、权限、来源与验证反馈

推理侧负责：
- 理解已经提供的任务
- 根据可见证据进行判断
- 遵守约束和输出契约
- 识别冲突、不确定性与不能回答的边界
```

基础模型、提示词、few-shot 示例和推理策略通常属于推理侧优化。检索、记忆、工具、
权限、状态管理、上下文路由和多 Agent 协作通常属于系统侧优化。

Prompt 有时会跨越两边：如果 Prompt 没有提供必要业务规则，这是信息供给问题；如果规则
已经清楚写出，但模型仍然反复误用，则更接近推理问题。

## 第一项测试：同输入可解性

第一步不是让人类随意解决任务，而是冻结模型在决策时看到的完整输入：

```text
用户请求
+ 系统指令
+ 检索结果
+ 工具返回
+ 历史状态与记忆
+ 其他 Agent 的交接内容
+ 输出格式和验收规则
```

然后把这份完全相同的信息交给具备相关能力的人类专家。

### 人类能稳定做对，模型做不对

这说明任务所需信息已经存在。下一步应优先检查：

- 模型是否具备所需的领域推理能力
- Prompt 是否把目标和决策顺序说清楚
- 上下文是否过长，导致关键证据没有被使用
- few-shot 是否示范了错误模式
- 输出格式是否干扰了真实判断
- 模型是否需要先列证据再下结论

这类问题不应该默认通过增加 Agent 来解决。更多节点可能只是重复消费同一份充分输入，
并不能补上推理能力。

### 人类也做不出来

这时不能直接得出“系统问题”的最终结论，因为还有两种可能：

1. 输入缺少决定性信息。
2. 任务本身没有定义出唯一、可验证的正确结果。

因此还需要继续做信息增量测试和输出唯一性测试。

## 第二项测试：信息增量是否改变判断

如果人类后来获得了更多信息，并因此更容易做出正确判断，那么这个差异本身就是重要
证据。

设模型原来拥有的信息为 `I`，人类后来新增的证据为 `E`：

```text
模型：I -> 无法判断或判断错误
人类：I + E -> 可以稳定判断
```

如果 `E` 对结果具有决定作用，而模型在决策时看不到 `E`，我会优先把它归为系统侧问题。

系统需要回答的不是“怎样把更多文字塞进 Prompt”，而是：

```text
E 从哪里来？
谁有权限获取 E？
什么时候必须获取 E？
怎样判断 E 与当前任务相关？
E 应该交给哪个决策节点？
怎样保留 E 的来源、时间和可信度？
```

### 信息缺失可能发生在整条链路上

人类能看到、模型看不到，不一定只是“忘了检索”。常见断点包括：

| 断点 | 表现 | 系统应优化什么 |
| --- | --- | --- |
| 获取 | 数据存在，但 Agent 没有查询 | 检索、工具或触发条件 |
| 权限 | 人类能打开系统，Agent 无权访问 | 工具权限与授权边界 |
| 选择 | 返回大量材料，但关键证据未被选中 | 排序、过滤与重排 |
| 路由 | 一个 Agent 已获得证据，决策 Agent 没收到 | 状态共享与交接契约 |
| 时机 | 证据在决策后才到达 | 依赖关系与执行顺序 |
| 表达 | 原始信息过长、格式混乱 | 结构化、压缩与引用 |
| 可信度 | 结论存在，但没有来源或时间 | provenance 与新鲜度标记 |

这时真正要优化的是“正确的信息如何在正确的时间到达正确的决策者”。

## 第三项测试：输出是否有唯一的判断标准

即使信息完全相同，人类也可能给出多个合理答案。例如：

```text
“给我一个合理的架构。”
“选择最重要的风险。”
“把结果写得更专业。”
```

这些任务没有天然唯一输出。如果系统没有说明受众、成本、风险偏好、候选范围和验收
标准，那么人类与模型的差异未必来自能力，也可能来自任务契约不完整。

这种情况应该优先补充：

- 什么结果算正确
- 哪些取舍优先
- 哪些候选允许被选择
- 哪些证据必须引用
- 不确定时应该追问、拒绝还是给出条件结论
- 最终由什么测试、评审人或业务规则验收

如果多个答案都合理，却只把其中一个标成正确答案，那么首先需要优化评价器，而不是
要求模型猜中评价者没有公开的偏好。

## 一张诊断表

把三项测试合起来，可以得到下面的判断：

| 人类与模型的条件 | 更可能的问题 | 优先动作 |
| --- | --- | --- |
| 相同充分输入下，人类能稳定做对，模型不能 | 推理侧 | 检查模型、Prompt、示例与推理策略 |
| 人类必须获得额外证据才能做对 | 系统侧 | 补检索、工具、权限、路由、状态或时机 |
| 相同输入下，人类和模型都无法判断 | 信息不足或任务不可解 | 找决定性证据，允许追问或停止 |
| 相同输入支持多个合理答案 | 任务契约与评价侧 | 明确偏好、范围和验收标准 |
| 关键证据已经存在，但被大量噪声淹没 | 上下文设计侧 | 选择、重排、压缩和结构化 |
| 模型得到新增证据后仍然误判 | 推理侧仍有缺口 | 在信息充分基础上继续优化模型 |

这张表的价值不是给所有错误贴上永久标签，而是决定下一次实验应该改哪个变量。

## “更多信息”不等于“更长上下文”

信息对等原则很容易被误解为：只要模型做不好，就把更多日志、文档和历史都放进去。

但上下文长度不是信息质量。

真正有价值的是能够改变候选结论的证据。例如，判断一次 CI 失败的原因，下面这些信息
可能有区分能力：

- 失败步骤和完整错误日志
- 失败测试对应的实现代码
- 当前提交与上一个成功提交之间的 diff
- 运行环境和依赖版本

而把整个仓库、所有历史讨论和无关日志一次性塞给模型，可能让关键证据更难被找到。

所以系统优化不是不断增加上下文，而是提高信号质量：

```text
相关性
+ 完整性
+ 时效性
+ 来源可信度
+ 对决策的区分能力
```

## 三个具体场景

### 场景一：只给错误日志，却要求定位代码缺陷

Agent 收到一段测试失败日志，但没有仓库访问、相关代码或近期 diff。它给出一个听起来
合理但未经验证的原因。

人类工程师随后打开失败测试、实现代码和最近提交，找到了真正问题。

这里不能简单说“人类比模型更会调试”。人类实际获得了更多信息。系统应该让 Agent 也
能完成相同的证据链：

```text
失败日志
-> 定位测试
-> 检索实现
-> 查看近期变更
-> 运行最小复现
-> 根据证据判断
```

这是系统侧的工具与规划问题。

### 场景二：证据完整，但模型仍然误用规则

退款 Agent 已经拿到订单状态、付款时间、退款政策和用户请求。人类审核员根据同一份
材料可以稳定判断“不满足退款条件”，模型却忽略政策中的时间限制。

这时继续查询更多订单信息没有意义。应该检查模型是否能正确执行规则、Prompt 是否要求
逐条对照条件、是否需要先输出证据表再给结论。

这是推理侧问题。

### 场景三：多个 Agent 各自知道一部分，但没有形成共同证据

一个检索 Agent 找到了最新政策，另一个订单 Agent 找到了交易记录，最终决策 Agent 却只
收到两个自然语言摘要，没有来源、时间和字段对应关系。

这不是再增加一个“审核 Agent”就能自然解决的。系统需要明确交接契约：

```text
结论
+ 支持证据
+ 来源
+ 获取时间
+ 未解决项
```

问题发生在信息路由和证据表达，而不是 Agent 数量不足。

## 人类的专业知识算不算“额外信息”

这是这条原则最需要小心的边界。

人类专家并不是空白模型。他带着长期学习形成的知识、经验和模式识别能力。因此，比较
“相同输入”时，还要区分两类知识：

### 通用、稳定、属于任务能力的知识

例如，资深 Python 工程师知道字符串不可变、异常堆栈如何阅读、二分查找需要维护什么
不变量。这类知识通常属于执行任务所需的能力。

如果模型在输入充分时仍缺少这些通用能力，更接近模型或推理侧问题。

### 私有、实时、组织特定的知识

例如，公司当前退款规则、某个仓库今天的代码、一次运行的日志、用户的订单状态。这些
信息不应期待模型通过预训练“知道”。

如果人类依靠这些信息做对，而系统没有把它们提供给模型，就是系统侧问题。

一个实用判断是：

> 这条信息应该通过训练成为通用能力，还是应该在每次任务中从权威来源获取？

前者更接近模型能力，后者更接近系统供给。

## 一个最小复盘流程

每次 Agent 做错判断，我会建议按下面顺序复盘：

### 1. 定义失败的决策点

不要只说“最终答案不好”。指出是哪一个决策错了：漏检索、选错工具、错误路由、误读
规则、证据不足仍强行回答，还是输出没有满足契约。

### 2. 保存当时的输入快照

记录模型在那个时点真正看到了什么，而不是事后把所有系统信息都算作它“应该知道”。

### 3. 运行同输入人类测试

让具备相关能力的人只使用这份输入，记录他能否稳定完成，以及仍然会追问什么。

### 4. 记录人类新增了哪些信息

不要只记录“人类做对了”。记录他打开了什么文件、查询了什么系统、询问了谁、依据了
哪条规则。

### 5. 把新增证据注入原决策点

如果模型得到这些证据后可以做对，优先修复信息链路。如果仍然做不对，再优化模型、
Prompt 或推理步骤。

### 6. 用最小改动验证根因

一次实验只改变一个主要变量：补一条证据、调整一次路由、增加一个输出约束，或更换
模型。否则即使结果变好，也不知道真正起作用的是什么。

## 可运行的诊断规则

下面的代码不是自动评价 Agent 的系统，而是把复盘顺序编码成一个最小决策表：

```python
from enum import Enum


class Diagnosis(Enum):
    SYSTEM = "system"
    INFERENCE = "inference"
    CONTRACT = "contract"


def diagnose_failure(
    *,
    human_can_solve_same_input: bool,
    extra_information_changes_result: bool,
    one_defensible_output: bool,
) -> Diagnosis:
    if not one_defensible_output:
        return Diagnosis.CONTRACT

    if extra_information_changes_result:
        return Diagnosis.SYSTEM

    if human_can_solve_same_input:
        return Diagnosis.INFERENCE

    return Diagnosis.SYSTEM


assert diagnose_failure(
    human_can_solve_same_input=True,
    extra_information_changes_result=False,
    one_defensible_output=True,
) is Diagnosis.INFERENCE

assert diagnose_failure(
    human_can_solve_same_input=False,
    extra_information_changes_result=True,
    one_defensible_output=True,
) is Diagnosis.SYSTEM

assert diagnose_failure(
    human_can_solve_same_input=True,
    extra_information_changes_result=False,
    one_defensible_output=False,
) is Diagnosis.CONTRACT
```

最后一个默认分支归为系统侧，是因为在人类无法根据相同输入完成、又没有证明模型推理
失败时，系统应该先允许补充信息、追问或停止，而不是要求模型继续猜测。

## 它适合诊断什么

这套原则适合判断：

- Agent 为什么选错工具或路由
- RAG 答案为什么缺少关键事实
- 多 Agent 交接为什么丢失证据
- 自动审核为什么做出错误业务判断
- 编码 Agent 为什么在缺少仓库上下文时猜测实现
- 应该先升级模型，还是先完善检索、记忆和工具链

它特别适合那些同时包含“获取信息”和“根据证据判断”的任务，因为这两类责任最容易
混在一起。

## 它不能单独诊断什么

这不是所有 Agent 优化问题的统一答案。

它不能直接决定：

- 哪个模型的延迟、价格和吞吐更合适
- 安全策略拒绝是否符合产品要求
- 非确定性生成应该如何评价风格与创造力
- 人类本身也不擅长的超大规模搜索如何自动化
- 某项能力应该训练进模型还是长期保留为外部工具

它也不是严格的因果证明。人类专家可能带有未记录的隐性知识，模型可能偶然猜对，额外
信息也可能只是提高信心而没有真正改变答案。因此，这套方法应该作为故障定位的起点，
再通过最小对照实验确认。

## 与现有 Agent 工作流的边界

这条原则不会替代评测、Tracing、RAG 指标、工具调用日志和人工 review。它决定的是这些
证据应该用来回答什么问题：

```text
Tracing 告诉我们模型当时看到了什么。
同输入测试告诉我们现有信息是否足够。
信息增量测试告诉我们缺少什么。
任务契约告诉我们什么算正确。
模型评测告诉我们信息充分以后能否稳定做对。
```

我不建议把它扩展成一套沉重的多 Agent 元系统。很多时候，只要保存一次输入快照，让一名
专家完成一次受控复盘，就足以判断下一步应该改检索还是改推理。

## 常见误区

### 人类能做对，所以一定是模型太弱

不一定。先确认人类有没有打开额外页面、使用内部系统、询问同事或依赖未写出的组织
知识。只比较最终答案，不比较信息条件，会把系统优势误算成个人能力。

### 人类也做不对，所以一定要增加检索

不一定。任务可能本来就没有唯一答案，或者缺少业务偏好。此时继续检索只会增加材料，
不会产生判断标准。

### 给更多上下文总是系统优化

不是。无差别增加上下文可能降低信号密度。系统的职责是提供决策相关证据，而不是搬运
所有可获得数据。

### 换强模型和优化系统只能二选一

也不是。真实问题可能同时存在信息缺口和推理缺口。正确顺序是先让信息充分且可验证，
再比较模型能力，否则模型评测本身就不公平。

## 我的建议

在 Agent 失败复盘中，我会坚持下面几个做法：

1. 保存决策时点的真实上下文，而不是只保存最终输出。
2. 记录人类为完成任务额外获取了哪些信息。
3. 把“缺信息”和“不会推理”拆成两个独立实验。
4. 为 Agent 交接保留证据、来源、时间和未解决项，而不只传结论。
5. 允许系统在信息不足时追问或停止，不把猜测包装成答案。
6. 信息充分以后，再用固定样本比较 Prompt、推理策略和模型版本。

最重要的是，不要用更强模型掩盖缺失的信息链路，也不要用更复杂的编排掩盖模型已经拿到
充分证据却不会判断的问题。

## 小结

我会把这套判断压缩成三句话：

> 相同可见信息下，人类专家能做对而模型不能，优先优化推理侧。

> 人类依靠模型不可见的额外证据才能做对，优先优化系统侧。

> 相同证据支持多个合理答案，先优化任务契约和评价标准。

Agent 系统真正的职责，是让正确的信息在正确的时间，以可判断、可追溯的形式，到达正确
的决策者。模型的职责，是在这些信息已经充分以后完成判断。只有先做到信息对等，我们
对“模型能力”的评价才有意义。
