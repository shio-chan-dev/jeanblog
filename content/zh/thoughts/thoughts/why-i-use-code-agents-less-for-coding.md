> 核心结论：我开始少让 Code Agent 直接写代码，并不是因为它变弱了，而是因为它越能一次完成复杂任务，我越容易把本该由自己掌握的模型、边界和工程判断一起交出去。以后我仍然会高频使用 AI，但会把它更多放在方案讨论、代码分析、反例检查和低决策密度实现上；核心模型和关键逻辑由我自己负责。

## 目标读者

- 已经在使用 Codex、Claude Code、Cursor 等编程 Agent，但越来越难审核其产出的开发者
- 发现项目推进得很快，自己却越来越不了解实现的人
- 想继续利用 AI，又不愿失去设计能力和代码所有权的个人开发者或团队负责人

## Agent 越来越强，我却越来越不想把任务整个交给它

Code Agent 的能力确实在提高。

它可以搜索整个仓库、追踪调用链、同时修改多个文件、运行测试，再根据报错继续修复。以前需要来回问答很多次的任务，现在一句目标描述就可能让它工作十几分钟，最后交回一个看起来完整的实现。

但我最近越来越常遇到另一种感受：**项目似乎推进了，我却不知道自己在项目里应该做什么。**

代码不是我写的，结构不是我定的，辅助函数也不是我拆的。Agent 告诉我测试已经通过，我接下来只能打开 diff，试着理解一个刚刚生成出来的陌生实现。

这时我的工作已经从创造变成了验收：

```text
以前：理解问题 -> 建立模型 -> 写代码 -> 调试自己的判断

现在：描述需求 -> 等待生成 -> 阅读陌生代码 -> 猜测它的判断 -> 调试它的实现
```

表面上，写代码的时间减少了；实际上，理解、验证和接管代码的成本被推迟到了最后。

对一次性脚本，这个交换可能很划算。对需要长期维护的项目，它未必划算。

## 能完成任务，不等于适合拥有实现

我以前容易把两个问题混在一起：

1. Agent 有没有能力写出这段代码？
2. 我应不应该把这段代码交给 Agent 写？

第一个问题谈能力，第二个问题谈责任。

即使 Agent 能写出能运行、能通过测试的实现，也不代表我应该放弃对其中工程决策的掌握。因为代码不只是语法，它还是一组被压缩后的判断：

- 数据到底怎样建模
- 状态由谁拥有
- 哪些转换允许发生
- 哪些条件必须始终成立
- 失败时回滚什么
- 并发时以谁为准
- 哪个接口会成为长期边界

这些判断可能只占几十行，却决定了以后几千行代码怎样生长。

如果它们由 Agent 默默替我决定，我得到的不只是代码，还得到了一组自己没有参与形成、却必须长期负责的假设。

所以我现在更在意的不是“Agent 能写多少行”，而是“这段代码的决策密度有多高”。

## 用决策密度重新划分人和 AI 的工作

这里的“决策密度”不是一个严格指标，而是一个判断任务归属的简单方法：一段代码里包含多少业务含义、状态约束、长期接口和高代价取舍？

代码量和决策密度并不成正比。

一个三十行的退款状态转换，可能同时涉及资金、幂等、事务和审计，决策密度很高。一个五百行的后台 CRUD，可能只是重复项目里已经确定的模式，决策密度反而较低。

我现在倾向于这样分工：

| 工作 | 决策密度 | 我的边界 |
| --- | --- | --- |
| 领域对象、状态机、不变量 | 高 | 我先设计，AI 负责挑战和找反例 |
| 核心业务逻辑、权限、资金与一致性 | 高 | 我自己实现或逐段掌握，AI 负责测试与审查 |
| 公共 API、数据库结构、跨模块边界 | 高 | 我做最终决定，不让 Agent 自行扩张范围 |
| 调用链检索、陌生代码解释、影响面分析 | 中 | AI 主做，我回到源码确认关键结论 |
| 已有模式下的 CRUD、DTO、数据转换 | 低 | 可以交给 Agent，但必须给出边界和验收条件 |
| 测试样例、文档、脚本和胶水代码 | 低到中 | 适合交给 Agent，再检查是否忠于真实契约 |

“胶水代码”不等于没价值。它仍然可能连接关键系统，也可能引入错误。这里真正的区别是：它通常不应该重新定义领域含义，而且可以通过现有接口和测试独立验收。

## AI 仍然适合什么

我并不打算停止使用 AI。相反，在下面几类工作中，它仍然非常有价值。

### 1. 和我一起建模，但不替我拍板

我可以先提出自己的模型：有哪些对象、状态怎样变化、哪些不变量必须成立。然后让 AI 扮演反方：

- 有没有遗漏的状态？
- 哪个对象承担了过多职责？
- 哪个边界在并发下会失效？
- 有没有更小的模型可以表达同样行为？
- 当前设计在哪些输入下会自相矛盾？

AI 很适合快速生成反例和候选方案，但最终模型必须由我选择，并且能由我解释。

### 2. 分析已有代码

当我进入陌生模块时，AI 可以帮我搜索入口、整理调用链、枚举相关测试、找出可能的影响面。它在这里提供的是检索和压缩能力，不是在替项目创造新的规则。

我仍然需要打开关键文件确认结论，但不必从几百个文件里盲目寻找起点。

### 3. 比较方案和暴露取舍

当我已经明确问题后，可以让 AI 比较两三个具体方案：复杂度在哪里，失败模式是什么，未来变化会影响哪一层。

这种讨论的产物不是直接合并的代码，而是帮助我做决定的材料。即使 AI 的某个方案最终没有采用，它也可能让我更清楚为什么选择当前设计。

### 4. 实现边界清楚、模式已经存在的部分

如果接口、数据模型、错误语义和验收测试都已经确定，Agent 写实现的可靠性会高很多。

这时它不是从零设计系统，而是在完成一个受约束的工程变更。例如：按照仓库已有模式补一个 DTO、实现一组简单映射、为确定行为增加测试，或者完成一个输入输出明确的小工具。

## AI 不适合替我做什么

至少在我的当前工作流里，下面几类任务不适合直接托管给 Agent：

- 从一句产品需求出发，自行设计并完成整个功能
- 决定核心领域模型、状态机和跨模块边界
- 编写我无法解释的关键业务逻辑
- 自行处理资金、权限、安全、迁移和并发一致性
- 在缺少验收条件时进行大规模重构
- 为了让局部任务通过而新增依赖、修改配置或引入新的抽象层

这不是说 AI 永远不能参与这些工作。它可以研究、提问、提供候选设计、写测试草稿，甚至在边界完全确定后实现其中一小段。

我拒绝的是“无人拥有决策的自主实现”，而不是 AI 参与核心问题。

## 我准备采用的新工作流

我更想把人和 Agent 的协作顺序改成这样：

```text
我定义问题和成功标准
-> 我建立数据模型、状态转换和不变量
-> AI 挑战模型并补充反例
-> 我确定接口、边界和允许修改的范围
-> 我编写核心逻辑
-> Agent 补测试、胶水代码和重复实现
-> AI 分析 diff 与潜在风险
-> 我确认自己能解释最终行为
```

这套流程不要求所有代码都必须由我逐字符输入。真正不可让渡的是设计权、解释权和最终责任。

如果某段核心实现由 AI 生成，但我能从模型推导它、能解释每条失败路径、也能在没有原对话的情况下继续修改，那么它仍然可以被我接纳。反过来，如果代码能跑但我无法说明为什么正确，我会把它视为验收失败。

## 一个最小的任务分配方法

以后决定是否让 Agent 写代码前，我会先问五个问题：

```text
1. 这项任务是否正在定义新的业务含义或系统边界？
2. 出错后是否会影响资金、权限、数据一致性或长期兼容性？
3. 我是否已经能说清数据模型、状态转换和不变量？
4. 仓库里是否已有可以直接遵循的实现模式？
5. 结果是否能由测试或其他独立检查明确验收？
```

分配规则很简单：

- 第 1 或第 2 题回答“是”：由我主导设计和实现，AI 只辅助
- 第 3 题回答“否”：先讨论和建模，不进入代码生成
- 第 4 和第 5 题都回答“是”：适合交给 Agent 实现
- 无法判断：继续缩小任务，直到边界可以说清楚

这个方法比“简单代码给 AI，困难代码自己写”更准确。真正需要人掌握的，往往不是语法最难的代码，而是承担最多决策的代码。

## 这不是退回纯手写

减少 Agent 直接写代码，会损失一部分短期速度。尤其在项目早期，直接让它铺出大量文件，进度看起来会非常快。

但那种速度只有在我能够接管结果时才有意义。否则，今天省下的实现时间，会变成明天的代码阅读、返工和维护成本。

另一方面，我也不需要因为担心失控就拒绝所有生成代码。对模式固定、风险较低、验收清楚的任务，坚持手写未必能增加多少理解，反而会消耗本可以用于建模和验证的注意力。

我真正想改变的是默认选项：

```text
以前：先让 Agent 完成，再决定是否接纳

现在：先由我完成关键判断，再决定哪些实现可以委托
```

Agent 以后还会继续变强，这条边界也可能移动。但能力提升不会自动转移责任。只要最终仍然是我维护项目，我就必须知道哪些决定存在、为什么这样决定，以及出问题时怎样修改。

## 结论

Code Agent 越来越强，意味着它可以替我完成更多操作；这并不意味着我应该把更多判断也一起交给它。

我现在更愿意把 AI 看成：

- 建模时的挑战者
- 设计时的方案研究员
- 阅读代码时的检索和分析助手
- 实现阶段处理低决策密度工作的协作者
- 测试与 review 阶段的第二双眼睛

而我自己需要重新站回最重要的位置：定义问题，建立模型，决定边界，编写或掌握核心逻辑，并对最终代码负责。

我不是在放弃 AI 编程，而是在放弃一种让我逐渐失去代码所有权的使用方式。
